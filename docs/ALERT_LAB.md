# 디버그 전용 알림 시뮬레이터

## 구조
- 실제 APK(release): `AlertLabMode.enabled()`는 항상 false이며 디버그 Activity는 포함되지 않음.
- 개발 APK(debug): 설정 → '알림 테스트 모드'를 켜고 '알림 시뮬레이터 열기'로 실행.
- 테스트 모드 전환 시 기존 예약 알림 취소 및 위치추적 종료. 실제 모드로 전환 시 예약 재등록.
- 테스트 데이터는 실 API·실 GPS·Firestore·사용자 루틴을 변경하지 않음.
- 알림 출력은 실제 `NotificationHelper.show`, 기록은 `AlarmLogRepository.write` 사용. 테스트 제목/로그에는 `[TEST]` 또는 `test:` 접두사를 붙임.
- 시뮬레이터의 가상 시각은 화면상의 fixture 시간에만 적용됨. 시스템 시계·AlarmManager는 변경하지 않음.
- 10종 일괄 검사는 모의 정상·경계 실패·정보 불확실 fixture에 대한 순수 조건 확인. 세부 수치 입력은 단일 실행의 일부 조건에만 반영. 환승·하차·도착 시 실제 StagePositionMatcher나 원래 TravelAlertMonitor 실행 경로 전체를 통과하지는 않음.
- 테스트 모드에서 실제 예약 발송 및 TrackingService 시작을 차단. 앱을 비정상 종료하고 재시작해도 debug 전용 로컬 플래그가 남을 수 있으므로 테스트 후 반드시 실사용 모드로 복귀.

테스트 결과가 아닌 구현 명세. 최신 Android 빌드와 기기 실험은 아직 수행하지 않음.

## 전체 자동 검증 버튼 (추가)
- 디버그 빌드에서 설정 > 알림 테스트 모드 ON > 알림 시뮬레이터 > **전체 알림 자동 검증 시작 (한 번 실행)**.
- 실행 후 전체 보고서가 화면에 출력되고 클립보드에 자동 복사됨. '최근 전체 검증 결과 다시 복사' 버튼으로 다시 복사 가능.
- `PASS`: 실제 production 순수 엔진 또는 Android API/DB 호출의 해당 조건을 직접 검사해서 성공함.
- `FAIL`: 단언 실패, 권한 거부, 알림 요청 거부, 로그 누락 등의 검증 실패. 예외도 가능한 범위에서 실패로 기록.
- `NOT_RUN`: 실제 이동/백그라운드/외부 API 등 이 버튼만으로 검증할 수 없는 항목. PASS로 계산하지 않음.
- 10종 시스템 알림은 실제 `NotificationHelper`를 통해 요청되며 `[TEST]` 제목과 `test:` DB 로그로 남음. **notify() 호출 성공은 사용자 화면 수신·팝업 표시 보증이 아님**.
- 검사 내용은 시간 및 주간 일정, 차량 ETA 수명·경계, 보행 여유, 경로 단계 판별, GPS 오류, 지연, 경로 이탈, 목적지 완료, 구간별 중복 방지·재발송 쿨다운, 기기 알림 채널/권한, 10건 발송 요청, Room 쓰기/읽기임.
- 환승·하차 경계 검사는 순수 거리·지속시간 조건만 평가하며 실제 `TravelAlertMonitor` 통합 실행은 하지 않음. 날씨 기상 예보 발송 수신기도 미실행.
- 검증용 ledger 키는 실행별 별도 테스트 ID를 사용하고 검사 종료 후 제거. 기존 사용자 경로, Firebase 동기화 및 실제 API를 변경하지 않음.
- **현재 자동화는 실제 Android 빌드/기기 실행 전 코드 반영 상태**이며, 결과 값은 사용자의 Android Studio 실행 후 보고서로 확인해야 함.

## 실 API 양식 및 한계 진단 (추가)

디버그 빌드의 설정 > 알림 테스트 모드 ON > 알림 시뮬레이터 > **실제 API 양식·응답·오류 진단 실행**.

- 진단은 실제 호출을 수행하므로 인터넷과 `local.properties`의 `SEOUL_SUBWAY_API_KEY`, `TAGO_BUS_SERVICE_KEY`, `KMA_SERVICE_KEY`가 필요함. 누락되면 `SKIP=KEY_MISSING`으로 보고함.
- 경로 검색/추천 TMAP API는 호출하지 않음. 사용자 저장 루틴이나 현재 GPS도 사용하지 않고 샘플 위치로 호출함.
- **1회 최대 5요청**: 서울 지하철 '서울'역 도착 1건, TAGO 서울역·수원 지역 정류장 검색 각 1건 + 데이터가 있으면 해당 정류장 도착정보 1건, 기상청 서울 격자(nx=60,ny=127) 단기예보 1건.
- **시간 제한 없음**을 기기 내부 debug SharedPreferences에 저장해 반복 호출을 차단. 버튼 중복 탭도 비활성화함.
- 응답 HTTP 상태, 처리시간(ms), 응답 글자 수, 제공기관 결과 코드, item 개수, 최상위 필드 이름, 핵심 필드 유무, ETA 필드 수, 기상청 TMP/PTY/POP 항목 수 및 예보 범위를 보고함.
- API 키, 원본 URL, 응답 본문, 제공기관 정류장 식별자는 보고서에 출력하지 않음. 단, `FIEL​​DS`는 필드 *이름*만 출력하며 개인 데이터 값은 출력하지 않음.
- TAGO의 첫 샘플 정류장 데이터가 없는 경우 연쇄 도착정보 호출은 건너뜀. 개별 호출 실패와 응답 형식 오류를 구분함.
- 진단 버튼 실행 후 보고서는 자동으로 클립보드에 복사되며 `최근 API 진단 보고서 다시 복사`에서 다시 복사 가능.
- `HTTP=200`이 곧 실시간 ETA 성공은 아님. 0건 응답은 스키마·가입상태·제공시간대·샘플 좌표 영향 가능. 실제 사용자의 루틴과 노선/방향 일치 여부는 별도 검증이 필요함.
- API 제공기관의 공식 일일 한도 자체를 테스트로 확정하지 않음. 부하·한도 소진 실험을 피하기 위해 반복 스트레스 테스트는 제공하지 않음.
- 전체 검증 버튼의 기존 가상 데이터 검사와 실 API 진단 버튼은 독립적으로 실행됨.

테스트 소스: `app/src/debug/java/com/example/mycommute/debug/ApiProbe.java`. 삭제하려면 해당 파일과 `AlertLabActivity.java`의 진입 버튼·호출을 함께 제거.

## 지하철·TAGO 세부 원인 검사 (2026-11-19)

이전 결과: 서울 지하철 HTTP 200 / 102자 / `status,code,message,link,developerMessage,total` (정규 도착 JSON 아님); TAGO 서울역 부근 HTTP 200 / providerCode 00 / 정류장 0건. 기상청 정상.

진단 개선 사항:
- 지하철 응답에 `status/code/message/developerMessage`가 있으면 `GATEWAY_ERROR`로 구분. 오류 메시지 원문 대신 `MESSAGE_CLASS`를 출력하며, 안전한 영숫자 오류 코드만 출력.
- 지하철 정상 `realtimeArrivalList`, `errorMessage`, `RESULT` 구조와 기타 예상 밖 구조를 각각 구분.
- TAGO `body.totalCount`, `body.items`, `body` 필드 목록과 빈 목록을 구분. 정상 빈 목록을 JSON 파싱 오류로 취급하지 않음.
- TAGO 샘플 검색을 서울역(37.555, 126.972)과 수원(37.2655, 127.0000) 두 지역에서 수행해 지역별 데이터 존재 여부를 확인.
- 두 샘플에서 어느 쪽이든 유효한 정류소 ID를 찾으면 도착정보 요청 1회 수행.
- 지하철 1 + 서울시 버스 정류장 1 + TAGO 정류장 2 + TAGO 도착 1 + 기상청 1 = 최대 **7회 호출**, 시간 제한 없음.
- 네트워크가 실행되지 않은 항목은 `SKIP`, 정상 처리지만 검색결과가 비어 있으면 `EMPTY_RESULT`, 제공기관 오류는 `PROVIDER_ERROR`로 표기.
- 요청 URL, 인증키, 전체 응답 원문은 출력하지 않음. 제공기관 오류 메시지도 분류 레이블만 출력.

**한계:** 이 도구는 제공기관에 직접 접속해 원인을 추적하는 검사 도구이며, 검사 전에는 지하철 인증 문제인지 API 게이트웨이 문제인지 확정할 수 없음. 두 지역에서 정류장 결과가 비었다고 전국 전체 데이터가 없음을 뜻하지 않음.

## 서울 버스 별도 제공기관으로 분리 (신규)

- TAGO 좌표 조회는 서울 표본 정류장 0건, 수원 표본 35건이 확인되어 서울 구간 버스 조회 경로를 분리함.
- 서울 버스는 `SeoulBusClient`가 서울시 BIS `stationinfo/getStationByPos`로 인근 정류소를 조회하고 `arrive/getArrInfoByStId`로 해당 정류소의 노선별 도착정보를 요청.
- 앱에서 서울권으로 추정하는 버스 승차 좌표 범위: 위도 37.42~37.70, 경도 126.75~127.20. **이는 행정구역 판정이 아닌 보수적 공간 근사치**이며 경계 지역은 잘못 라우팅할 수 있으므로 실 운행 검증 필요.
- 서울 API는 **별도** `SEOUL_BUS_SERVICE_KEY`가 필요함. 개발자가 `local.properties`에 등록해야 함. 없는 경우 테스트에서 `SEOUL-BUS SKIP=SEOUL_BUS_SERVICE_KEY_MISSING`, 실제 앱에서는 데이터 없음 안내.
- 서울시 버스 응답은 XML이며 TAGO JSON 응답과 혼합해 파싱하지 않음. 안전한 XML 파서 설정과 다운로드 크기 제한을 사용함.
- 조회시 정류소 이름·좌표가 일치하지 않거나 방향별 정류소를 유일하게 특정하지 못하면 도착시간을 추정하지 않고 unavailable 처리. 도착시간은 노선명과 양수 ETA가 맞는 경우만 허용.
- 디버그 API 진단에 서울 버스 정류소 실제 호출 1건을 추가. 출발지 샘플은 서울역 부근이며 요청키 또는 호출 실패를 분류, XML 응답 코드와 항목 수를 표시. **한 번에 최대 6개 외부 요청**, 별도 시간 제한 없음.
- 기상청은 이미 통신/예보 스키마 확인 성공이므로 그대로 유지.
- 지하철 `INFO-200`(실시간 도착자료 없음)는 앱에서 unavailable로 반환하되 임의 ETA를 생성하지 않음.
- 현재 커밋은 **Android Studio에서 빌드/실 API를 직접 실행한 결과가 아직 없음**. 특히 서울시 버스 별도 키의 발급·승인과 근접 정류소/노선 매칭은 검증 필요.

## 공공데이터포털 동일 인증키 지원과 서비스별 권한 테스트

- `local.properties`의 `PUBLIC_DATA_SERVICE_KEY`를 **선택적 공통 키**로 사용할 수 있음. 이미 입력된 `KMA_SERVICE_KEY`, `TAGO_BUS_SERVICE_KEY`, `SEOUL_BUS_SERVICE_KEY`는 개별 설정이 우선하고, 누락된 항목은 공통 키로 대체. 이전 세 키가 모두 같아도 그대로 동작.
- 공공데이터포털에서 서비스마다 별도 활용신청/승인이 필요할 수 있으므로 키 문자열이 같다고 승인도 같다고 가정하지 않음.
- 진단 출력 `PORTAL_KEY_SHARED SEOUL_EQUALS_TAGO=... SEOUL_EQUALS_KMA=...`에는 불리언 일치 여부만 출력. API 키 원문, 해시, 요청 URL은 출력하지 않음.
- 서울시 버스 **정류소조회**와 **도착정보조회**를 독립적으로 검사함. 정류소조회가 401이더라도 공개 문서의 예시 정류소 ID `112000001`을 사용해 도착정보조회 권한/응답 형식을 별도 진단함. 샘플 정류소의 ETA가 실제로 있다는 보장은 없음.
- 각 엔드포인트의 `HTTP 401/403/429`, 제공기관 코드, XML 스키마, 빈 응답 여부를 분리해 출력함. 401만으로 어떤 신청이 누락됐는지 단정할 수 없음.
- 최대 요청 수: 지하철 1 + 서울 버스 정류소/도착 각 1 + TAGO 정류소 2/도착 1 + 기상청 1 = **7건/실행**.
- 공식 사용 가이드: 서울특별시 버스도착정보조회 서비스 Open API 활용가이드 (2025-08-14 사용자 제공).

## 서울 버스 401/406 추가 진단 및 공식 엔드포인트 수정 (2026-11-19)

- 직전 406의 원인이 `Accept: application/json`에 있는지 확인하기 위해 서울 버스 호출만 `Accept: application/xml`로 변경.
- 서울 **정류소조회** 검사: 문서에 명시된 `stationinfo/getStationByName?stSrch=서울역` 사용.
- 서울 **도착정보조회** 검사: 제공된 2025-08-14 공식 활용가이드의 `arrive/getArrInfoByRouteAll?busRouteId=100100118` 사용. 샘플 노선 ID는 문서상 예제이며 실제 운행을 보장하지 않음.
- 잘못된/미검증 `arrive/getArrInfoByStId` 호출 사용을 제거. 실제 앱의 서울 버스 조회는 `getStationByName` → `getRouteByStation?arsId=...` → `getArrInfoByRouteAll?busRouteId=...` 순서로 연동. 정류소 ID, 노선명, 좌표를 확인하고 유일하게 확정할 수 없는 경우 도착시간을 표시하지 않음.
- `exps1`, `exps2`처럼 문서에서 **초 단위**라고 명시한 필드만 ETA로 허용. 단위/해석이 불확실한 `traTime`은 사용하지 않음.
- 디버그 보고서에 `MEDIA_TYPE=XML/HTML/JSON/OTHER`, `ERROR_BODY_CLASS`를 추가해 406/401 시에도 키나 응답 전문을 노출하지 않고 서버 응답 종류를 구분.
- **현재 실제 API 재검증과 Android Studio 빌드는 아직 미실행**. 401/406이 해결됐다고 단정할 수 없음. 수정된 진단을 실행해 성공 여부를 확인해야 함.
