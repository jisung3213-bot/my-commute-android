# 개발 변천사·브랜치 분리·변경 의사결정

> 기준: 2026-11-20. 이 문서는 GitHub의 기존 `README.md`, `docs/STATUS.md`, 코드 변경 비교 및 대화에서 확인된 작업을 시간순으로 재정리한 자료다. 기능의 **과거 개발 단계**와 **현재 최종 동작**을 혼동하지 말 것. 현재 기능의 파일별 구조는 [ARCHITECTURE_CURRENT.md](ARCHITECTURE_CURRENT.md)에 기술한다.

## 1. 브랜치 현황과 분리 이유

2026-11-20 조회 시 GitHub에 확인된 브랜치는 **`main`**, **`feat/isolated-alert-lab`** 두 개다. 비교 결과 개발 브랜치는 `main` 대비 **111커밋 앞서고 0커밋 뒤처져 있었음**(조회 시점의 스냅샷; 이후 문서 커밋으로 커밋 수가 증가함).

| 브랜치 | 목적 | 사용 원칙 |
|---|---|---|
| `main` | 기본 코드라인 및 비교·복귀 기준 | 광범위한 UI/실시간 네트워크/테스트 실험을 무조건 합치지 않음 |
| `feat/isolated-alert-lab` | 실제 알림 10종, 설정 화면, **격리된 디버그 시뮬레이터**, 이후 실시간 교통/GPS/UI·추천 로직 개선 통합 | 작업 중 기능을 이 브랜치에 모아 테스트한 뒤 안정화·검토할 수 있게 함 |

### 왜 브랜치를 나누었나

1. **알림 테스트 격리**: 가짜 알림을 실제 GPS·실제 출퇴근 예약·Firestore 변경으로 오인하거나 정상 사용자의 알림 상태를 오염시키지 않게 하기 위함. `app/src/debug/`에 실험 UI를 따로 두고, `AlertLabMode`에서 운영 동작을 중지하도록 구성함.
2. **안정된 비교 기준 유지**: GPS Foreground Service, 예약 알림, 경로 캐시, API 조회, Room 로그는 결합도가 높으므로 모두 동시에 수정 시 회귀 원인을 구분하기 어려움. `main`을 보존해 변경 내용을 비교할 수 있게 함.
3. **미검증 작업과 정상 기능 분리**: 실제 TMAP 바이너리, 발급키, 기기/에뮬레이터 테스트가 없는 환경에서 작성한 커밋은 코드 반영이 곧 동작 검증은 아님. 그래서 기능 검증 전 무조건 기본 브랜치에 합치지 않도록 함.
4. **디버그 모드의 배포 분리**: Gradle의 `src/debug/`가 `src/main/` 및 release 소스와 다른 목적을 가지도록 함. 이것은 Git **브랜치 분리와 별개의 빌드 변형 분리**이며, 둘을 혼동하지 않아야 함.

> **중요:** 브랜치 생성 당시의 구체적인 팀 합의 문서/설명은 현재 Git 기록 비교로 증명할 수 없다. 위 이유는 브랜치명, 기능 구조 및 작업 맥락에서 확인되는 **설계상 분리 목적**을 문서화한 것이며, 특정 사람의 당시 의도를 단정하는 기록은 아니다. 또한 브랜치명과 달리 현재 `feat/isolated-alert-lab`에는 알림만이 아니라 UI·API·경로 추천 개선도 함께 누적되어 있다.

### PR과 병합

- 검토용 PR: [#1](https://github.com/jisung3213-bot/my-commute-android/pull/1).
- 이 문서 갱신에서는 **병합하지 않음**. `main`의 코드를 임의로 바꾸지 않음.
- 병합 전에 실기기 빌드·핵심 API·GPS·알림 수신 회귀 검증을 진행하는 것이 설계상 필요하지만, 이 기록은 테스트 완료 선언이 아니다.

## 3. 해결된 문제와 설계 선택

### 3.1 지하철 ETA가 빈 이유

- 서울시 지하철 실시간 API는 ETA 필드 `barvlDt`를 제공하나 값이 항상 양수는 아님.
- 사용자가 **2026-11-19 20:18:56 KST**에 실행한 12역 표본 조사: **총 150행 중 양수 67, 0초 83, 누락 0**.
- 광운대역(1호선) 6행 모두 0초, 서울역/시청/종로3가 등에는 일부 양수. 2호선의 조사 표본은 양수 비중이 높았음.
- 이에 따라 **정확하지 않은 ETA 숫자는 출력하지 않고**, 열차 상태·방면만 사용자 화면에 표시. 디버그용 원본 ETA·시각은 운영 카드에서 제거. 이 표본은 전 노선·전 시간대 통계가 아님.

### 3.2 GPS 추적과 테스트 모드

- 초기에는 추적 서비스를 요청한 것과 실제 Fused Location 업데이트 시작 성공을 구분하기 어려웠음.
- 서비스 상태/중지 사유 표시, 권한 및 기기 위치 서비스 점검, 알림 실험 모드로 인한 중지 사유를 노출하도록 조정.
- **디버그에서 GPS 마커를 조작하는 것은 실제 Android GPS 좌표를 바꾸지 않는다.** `RouteGpsLabActivity`는 도식의 0~100% 모의 위치 및 `StagePositionMatcher` 판정 시험만 제공.
- 터널·겹치는 경로·권한·기기 정확도 등에서 실제 위치 판정은 여전히 제한됨.

### 3.3 알림 문구가 테스트에 반영되지 않던 문제

- 실제 `ReminderReceiver`/`TravelAlertMonitor`에서 문자열을 변경해도 시뮬레이터가 `[TEST] ... 모의 데이터 기준...` 고정 텍스트를 사용해 문구가 달랐음.
- `AlertCopy`를 공통 생성자로 분리하고 실제 발송·개별 시뮬레이터·10종 일괄 검사에 연결.
- 테스트는 제목에만 `[TEST]` 표기를 추가하고 입력 사실은 모의 값. 실제 ETA가 없는 상태에서 임박 알림을 만들어내지 않음.

### 3.4 추천 1개만 먼저 보여주는 이유

- 후보 여러 개를 모두 펼치면 사용자가 비교해야 할 정보가 과밀해짐.
- 기상·루틴 여유에 따라 점수로 순위를 매겨 **최상위 추천 1개**를 먼저 보여주고, 대체 경로는 버튼으로 펼침.
- 추천 순위는 사용자가 확정한 루틴 선택과 별개. 추천 결과가 표시됐다는 이유만으로 사용자의 기존 선택을 덮어쓰지 않음.
- 하드코딩된 화면별 정렬 로직을 순수 엔진 `WeatherRouteRanker.rank()`로 통합하여 **디버그 테스트와 실 앱 순위 차이를 줄임**.

## 4. 소스셋 분리와 테스트의 의미

```text
src/main/   = 실제 앱 화면·엔진·서비스·API 클라이언트 (debug/release 공통)
src/debug/  = 테스트 Activity 및 모의실험 구현 (debug 빌드 전용)
src/test/   = 로컬 JUnit 테스트 (APK 실행 화면과 별개)
```

- `src/debug/`의 일괄 알림 테스트가 성공했다고 해서 `TrackingService`의 잠금화면·절전 모드 알림이 정상인 것은 아님.
- `src/test/`의 단위 테스트는 **앱의 Run과 무관하게 별도 실행**한다. 과거 사용자 PC에서 클래스 로딩 오류가 있었고, 그것만으로 APK 실행 불가를 의미하지 않음.
- API 실측과 순수 로직 테스트, 실제 기기 종단간 검증은 서로 구분해 기록한다.
